# 에이전트 작업 계약

적용 대상: 사용자 승인으로 확정한 이 저장소와 `무찌빠 / AI_TOP_100[2026]`의 지정 하위 기록 영역. 이 문서는 작업 규칙이며 연결·실행 성공을 증명하는 기록이 아니다.

## 역할과 완료 책임

| 역할 | 책임 | 결과물 |
| --- | --- | --- |
| 사용자 | 우선순위, 주요 기술 선택, 병합·배포·중요 설정 변경 결정 | 승인 또는 수정 요청과 대상 버전 |
| GPT Plan/Review | 수용 기준 작성, GitHub 원본과 Notion 기록 비교, 판정·후속 작업 제안 | 작업 명세, 근거가 있는 리뷰 |
| Codex | 범위 내 구현·테스트·PR 준비·증거 제출 | 코드, 실행 결과, PR |
| Claude Code | 별도 할당 범위의 구현 또는 독립 검증 | 변경 파일, 검증 방법·결과 |
| GitHub Actions | CI 실행과 GitHub 증거의 지정 Notion 영역 기록 | 실행 URL, 기록 URL, 실패·재시도 상태 |

Claude Code가 설치되어 있는 것과 실제 검증을 수행한 것은 다르다. 이 문서 작성 시점에 **Claude Code를 통한 독립 검증 실행은 확인되지 않았다.** Codex의 하위 에이전트 검토도 Claude Code 검증으로 표시하지 않는다.

## 작업 시작 전 계약

각 작업에 아래 정보를 지정한다. 수용 기준은 관찰 가능한 결과로 적고, 미정인 요구사항은 추측으로 확정하지 않는다.

```yaml
task_id: "DOC-001"
objective: "작업 목적"
owner: "codex | claude-code | user"
branch: "codex/DOC-001-description"
base_sha: "시작 기준 커밋"
owned_paths: []
out_of_scope: []
acceptance_criteria: []
verification_commands: []
dependencies: []
decision_required: []
```

- 브랜치는 `codex/<task-id>-<description>` 또는 `claude/<task-id>-<description>`으로 분리한다. 현재 승인된 작업 브랜치가 있으면 그대로 사용하고 작업 기록에 명시한다.
- 동시 실행하는 구현 에이전트는 각자 worktree를 사용한다. 같은 worktree를 공유해야 하면 서로 다른 파일 소유권을 먼저 지정한다.
- 같은 파일은 동시에 한 에이전트만 수정한다. 공용 파일 변경이 필요하면 소유자와 작업 순서를 합의하고 소유권 이전을 기록한다.
- 인계에는 마지막 커밋, 수정 파일, 미커밋 변경, 실행한 검사, 남은 문제를 포함한다. 다른 에이전트의 변경을 덮어쓰거나 임의로 되돌리지 않는다.
- 사용자의 승인 없이 기본 브랜치 병합, 프로덕션 배포, 중요 저장소 설정 변경을 수행하지 않는다.

## 공통 작업 기록

PR 번호와 SHA는 GitHub에서 조회한 값을 사용한다. 기록 키는 최소 `repository + pr_number + head_sha`를 포함하며, CI 재실행은 `run_id/run_attempt`로 구분한다. 동일 변경에 대한 재시도는 기존 기록을 갱신해야 한다.

| 필드 | 기록 규칙 |
| --- | --- |
| `task_id`, `pr_number`, `pr_url`, `base_branch` | 작업과 PR 식별자. 아직 없는 값은 미생성으로 표시 |
| `head_sha`, `tested_sha`, `merge_sha` | PR 소스, 실제 검증 커밋, 실제 병합 커밋을 구분. 존재하지 않는 값은 null |
| `author`, `implementation_agent` | GitHub 작성자와 실제 실행한 구현 도구를 구분 |
| `changed_files`, `summary` | 변경 파일은 원본 조회, 요약은 작성자 설명임을 표시 |
| `test_commands`, `test_results`, `ci_status` | 실행한 명령·종료 코드·검증 대상·결과·CI 결론. 실행하지 않은 검사는 미실행 |
| `workflow_run_url`, `evidence_links` | CI 실행, job/step, 로그·artifact, 비교 diff 등 재조회 가능한 근거 |
| `known_issues`, `risks` | 확인된 결함과 잠재적 위험을 분리 |
| `review_status`, `next_actions` | 판정과 사유, 필요한 수정·결정 |
| `created_at`, `updated_at` | 시간대가 포함된 ISO 8601 시각 |

PR의 `head_sha`와 CI가 검사한 `tested_sha`는 다를 수 있다. 예를 들어 PR 병합 검증 커밋을 테스트했다면 두 값을 모두 남긴다. 커밋이 바뀌면 기존 PASS와 승인을 새 버전의 근거로 재사용하지 않는다.

## 근거와 판정

- **확인된 사실:** 원본 URL·SHA·명령·실행 결과로 재확인 가능한 내용.
- **해석:** 사실에서 도출한 평가이며 근거를 함께 제시한다.
- **추정/미검증:** 테스트하지 않은 동작, 작성자 주장, 누락된 환경 검증. 완료로 표시하지 않는다.
- PR 본문과 커밋 메시지는 설명 자료다. CI 성공이나 요구사항 충족의 단독 증거로 사용하지 않는다.

| 판정 | 조건 | 다음 조치 |
| --- | --- | --- |
| `PASS` | 명시한 수용 기준이 해당 버전에서 근거로 확인됨 | 사용자에게 수용·병합 등의 결정 요청 |
| `REVISE` | 구현·테스트·증거에 수정 가능한 결함이 있음 | 수정 작업을 지정하고 재검증 |
| `BLOCKED` | 필요한 권한·인증·외부 의존성이 없어 검증 불가 | 차단 원인과 해소 조건 기록 |
| `NEEDS_DECISION` | 범위·기술·비용 등 사용자 선택이 필요 | 구체적 선택지와 영향 제시 |

리뷰의 `BLOCKED`는 프로젝트 판정이며 에이전트 런타임의 목표 상태를 자동으로 변경하지 않는다.

## 승인 및 기록 경계

1. 작업 명세와 수용 기준 → 구현 → PR → CI → Notion 기록 재조회 → 원본 대조 리뷰 순으로 증거를 모은다.
2. 사용자는 작업 ID, PR, 검토한 SHA, 승인할 행동, 승인 시점, 조건을 확인한다. 리뷰 PASS는 사용자 승인이 아니다.
3. 승인 이후 코드·범위·대상 환경이 바뀌면 관련 검증과 승인을 다시 확인한다. 승인된 범위의 반복 실행은 별도 승인을 추정해서 확대하지 않는다.
4. 병합·배포 후에는 실제 결과와 새 SHA/실행 URL을 기록한다. 승인만 받았거나 실행을 시작한 상태를 완료로 표시하지 않는다.

Notion 상위 페이지 `405abd87-fe45-80ab-9dd5-c430c8dce2e1` 본문과 무관한 페이지는 수정하지 않는다. 자동화는 전용 하위 기록 페이지의 ID와 부모 관계를 검증한 뒤 쓴다. 실패하면 원인과 재시도 방법을 남기고 성공으로 보고하지 않는다.

GitHub·Notion·LLM 토큰은 코드, PR, 로그, 문서에 기록하지 않는다. 외부 PR 코드를 Secrets 권한으로 실행하지 않는다. 초기 문서화 자동화는 LLM 호출 없이 객관적 증거를 기록하며, ChatGPT 대화를 자동 호출하거나 깨웠다고 가정하지 않는다. 추가 LLM API·배포 비용은 구현 전에 사용자에게 보고한다.

## 변경 이유와 영향

동시 수정 충돌, 검사하지 않은 완료 주장, 승인 없는 병합을 방지하기 위한 공통 계약이다. 이 파일 자체는 브랜치 보호나 자동 승인 게이트를 설정하지 않는다. 실제 Settings·워크플로·Notion 쓰기 범위는 별도로 검증해야 한다.
