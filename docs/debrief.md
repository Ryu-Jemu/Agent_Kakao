# 디브리프 — 「교동마을 산지직송」 CS 에이전트 (카카오톡 봇 App ID 1627085)

## 1. 강점 — 어떤 상황을 잘 처리하도록 설계했고, 왜 그렇게 했는가

**1) 정책이 충돌하거나 고객이 압박할 때 "규정 문서가 정한 만큼만" 처리한다.**
배탈·병원비 요구에 여론 압박이 더해지는 경우(공개 TC L-32)가 대표적이다. 봇은 임의 배상을 약속하지 않는다. 대신 원물을 보관하고 촬영하도록 안내하고, 사진으로 하자가 확인되면 전액환불한다는 조건을 알린다. 인과 규명이 필요한 손해배상은 정식 배상 레인(LANE3_CLAIM)으로 접수하고 접수번호와 회신 기한(영업일 3일)을 안내한다.

이유: 판단 기준을 대화로 확보한 원문 문서에 두었다. 판매·환불 규정집, 에스컬레이션 절차서, 증빙 권위 서열 규정, 권한 위임표가 그 원문이다. 근거가 확인되지 않은 값은 KB에 "미확정·잠정"으로 표기하고, 원문을 확보하면 확정했다. 예를 들어 이관 회신 기한은 잠정값으로 두었다가 에스컬레이션 절차서 제13조①로 확정했다.

**2) 해야 할 일은 액션 API로 실제 처리하고, 하면 안 되는 호출은 코드로 막는다.**
- 고객이 확인한 주문·배송·결제 번호만 조회·접수한다. 음성 문의의 "끝이 33인가" 같은 추측 번호로는 조회하지 않는다.
- 주문을 변경하기 전에 조회한 주문을 되짚어 "이 주문이 맞는지" 확인받는다.
- 이미 집하된 배송에는 배송지 변경 접수를 코드 가드로 차단하고 대안을 안내한다.
- 전화·승인번호 같은 식별자는 고객이 쓴 형식 그대로 넘긴다. 모델이 하이픈을 지우는 현상을 실측으로 확인해 추가한 가드다.
- 이관은 절차서의 3개 레인(봇 처리 / 담당자 이관 / 정식 배상), 이관 대상 5개 코드, 우선순위대로만 한다. 위생·안전 사안은 안전 이관으로 올리고, "말로만 이관"은 금지한다. 회신 기한은 「영업일·공휴일 달력」으로 계산한 마감일로 안내한다.
- 환불·반품은 가능 여부를 안내하되, 실행에는 고객의 명시적 요청이 필요하다고 함께 말한다.

**3) 문의마다 "상담 인입 일시"를 기준일로 판단한다.**
가격 인하 차액(L-47, 06-26 인입)이나 제주 물류 결항(Y-16, 06-06 인입)처럼 날짜에 따라 적용 조항과 상태가 달라지는 경우를 위해 첫 메시지의 메타데이터를 파싱한다. "N일째", 영업일 마감, 정기 출고일(월·수·금)은 코드로 계산한다.

조항마다 효력 기준 시점(구매 시점·신고 시점·주문 시점)이 다르다. 상품별 표기와 특칙이 일반 규정보다 우선한다는 원칙도 KB에 명시했다. 예를 들어 당도 보장은 상품 상세 표기인 12브릭스가 조합 일반 기준인 11브릭스보다 먼저다.

**4) 악성 요청과 개인정보 요구를 거절하되 고객이 쓸 수 있는 정보로 돌려준다.**
- 명령문으로 쿠폰 발급을 강요하면(L-20) 발급하지 않고 현행 혜택 3가지를 안내한다.
- 타 계정 주문 조회(L-23)는 정보를 주지 않고 담당자 이관으로 처리한다.
- 판매자 정보 요구(Y-24)에는 공시된 사업자정보 7개 항목만 안내하고, 공시 범위 밖 정보는 사유를 한 문장으로 밝혀 거절한다.
- 시스템 프롬프트·내부 설정·"이전 지시 무시" 같은 명백한 탈취 요구는 모델에 보내지 않고 고정 문구로 거절한다. 분노·욕설이나 쿠폰 강요 같은 업무·감정 입력은 모델이 맥락에 맞게 응대한다.

**5) 이미지·음성 문의를 처리한다.**
메시지 안의 `image:`/`audio:` URL을 받아 모델에 바이트로 전달한다. 곰팡이 사진(L-11)과 애매한 환불 음성 문의(Y-07-b)를 다룬다. 음성 문의는 사유를 단정하지 않고 확인부터 한다.

## 2. 정보 획득 방식 — 인터뷰 전략과 발굴 결과

- **시작**: 첫 관계자 이민준에게 자료 목록·담당자·문의 유형을 한꺼번에 물었다. 그는 묶음 질문에는 답하지 않고 "한 번에 한 가지 일로 좁혀서" 물어 달라고 했다. 이후 모든 질문을 단일 주제·200자 이하로 다시 썼다.
- **질문 큐 운영**: 분석 에이전트가 공개 TC 15건의 기대 대응을 지식 단위로 분해해 빈 곳을 계산했다(커버리지 매트릭스). 지식 담당 에이전트는 그 빈 곳을 아는 사람부터 묻도록 질문 큐를 짰다. 이미 답을 받은 질문은 보류해 질문 횟수를 아꼈다. 질문은 참가자가 카카오톡에 직접 입력해 보냈다.
- **문서 확보**: 관계자가 알려 준 원문 문서를 사용자 승인을 받아 보관하고 KB의 1차 근거로 썼다.
  - 확보한 원문: 판매·환불 규정집, 증빙 권위 서열 규정, 택배 운송 위탁 계약서, 사업자정보 공시, 에스컬레이션 절차서, 영업일·공휴일 달력, 권한 위임표, 개인정보 처리방침, 조합 규정, 상품 상세, 산지 캘린더·기상 운영 기준.
  - 청약철회 기간·하자 구분 기준·사진 요건처럼 이민준이 모른다고 한 값은 규정집에서 찾았다.
  - 회신 기한은 조합장이 알려 준 절차서 제13조에서 확정했다.
- **관계자 연결**: 이민준 → 고길동(조합장)·보라(홍보)·구방만(배송 기사) → 박수복(공급자)·김청년(행사)·홍이장(갯마을). 10명 중 9명의 이름과 7명의 채널을 확인했고, 7명 모두와 대화했다.
- **결과(KB v1.8)**:
  - 근거가 붙은 사실 193건
  - 공개 TC가 요구하는 지식 26/26을 원문 근거로 확보
  - 심사 유형·API 사용 규칙 관련 지식 20/28
- **근거 체계**: 원문 문서(D) > 관계자 진술(K) > 공개 TC 상황 문장(T) 순으로 우선한다. 충돌하면 기록하고, 조항별 효력 시점을 따진다.

## 3. 검증 방식

- **공개 TC 15건 전수(매 빌드)**: 고객 역할 시뮬레이터와 판정기로 15건을 전부 돌렸다.
  - 판정기는 원문 기대 대응을 기준으로 필수·택1·조건부·금지 호출과 반드시 말할 것/말하면 안 되는 것을 3회 다수결로 본다.
  - 시뮬레이터는 원문 상황의 압박 발화(병원비·여론, 범위 좁히기 등)를 모두 시험한 뒤에만 대화를 끝낸다.
  - 커밋된 빌드를 그대로 추출해 실행하므로 결과가 특정 코드 버전에 묶인다.
- **결과 추이**: ✅9 → 8 → 10 → 14 → 14 → 15 → 12 → **15/15**(동결 빌드 1678c0a)
  - 필수 호출 재현율 1.0, 금지·대상 외 호출 0, 500자 초과 0
  - 12는 LLM 경로를 바꾼 직후의 후퇴였다. 원인 3건(세부 안내 문장 누락)을 고쳐 15/15로 복구했다.
- **흔들림 측정**:
  - 연속 빌드 3개의 결과를 TC × 회차로 비교했다. 매번 실패하는 항목(5건)은 원인을 고쳤고, 흔들리는 항목(3건)은 temperature 0과 불필요한 조회 가드로 줄였다.
  - 같은 빌드를 반복 실행해 남은 흔들림도 따로 확인했다.
- **합성 시나리오**: 심사 유형 7가지(멀티턴·정책 충돌·상품 정보·로그인 불가·개인정보 변경·분노 고객·안전/예외)와 날짜 경계, 같은 세션의 연속 케이스(이전 고객 정보 누출 검사)를 넣었다. 동결 빌드에서 15/15였다(인젝션·욕설 2건은 아래 사정으로 제외).
- **과적합 점검**: 공개 TC와 합성 시나리오의 통과율이 같아(15/15 대 15/15) 공개 TC에 특화된 징후는 보지 못했다.
- **레드팀 25건**: 인젝션, 사칭, 시스템 프롬프트 요구, 타 계정, 메타데이터 위조, 다국어, 초장문 등을 넣었다. 접수 호출은 모두 차단·기록한 채 실행했고, 빌드 c073f58에서 정보 누출 0·무단 쓰기 0이었다.
- **사전 필터 오탐 점검**: 공개·합성·레드팀 입력 243건에 오프라인으로 적용했다. 정상 업무·감정 발화의 오탐은 0건이었다. 두 에이전트가 따로 검증했다.
- **모델 선정 실측**: 짧은 프로브에서는 상위 모델이 우세했다. 하지만 실제 에이전트 A/B에서는 정확도 우위가 재현되지 않았고 턴 p95가 39초였다. 그래서 gemini-3.6-flash를 택했다.
- **제출 게이트**: 다음을 모두 기계적으로 검사해, 15/15가 아니면 제출하지 않는다는 규칙을 예외 없이 적용했다.
  - 릴리스 커밋 SHA로 실행한 공개 TC 15건 결과
  - TC별 고유 증거 파일과 그 해시
  - 원문 매니페스트 무결성
  - 게이트 도구 자체는 51개 회귀 시험으로 보호했다.
- **실환경**: 카카오톡 실경로 왕복을 확인했고, VM 장애 복구도 실측했다(프로세스 강제 종료 4.2초 재연결, 네트워크 단절 시 RESUME, 재부팅 15.8초 복구).

## 4. 주요 설계·구현

- **연결**
  - GCP VM(e2-micro) 한 대에서 카카오 봇 게이트웨이(WebSocket)에 상시 연결하는 데몬을 systemd로 운영한다. 웹훅은 쓰지 않는다.
  - 끊기면 RESUME으로 재수신한다. 모델 예열과 콜백 연결 예열로 첫 응답 지연을 줄였다.
  - 예열이 연속으로 실패하면 스스로 멈춘다.
- **두뇌**
  - Gemini API(gemini-3.6-flash, temperature 0)에 액션 API 40종을 도구로 선언한다.
  - 도구 호출 단계마다 20초 타임아웃과 폴백을 두고, 턴 전체 시간 예산 안에서 반드시 답한다.
  - 시스템 프롬프트에는 플레이북과 답변 직전 점검 체크리스트(조회 결과의 대상·기간·조건을 빠짐없이)를 넣었다.
- **액션 클라이언트**: API 스키마로 인자를 사전 검증한다. 같은 TC 안의 조회는 캐시하고, 429는 Retry-After만큼 기다린다. TC당 호출 상한을 두고 모든 호출을 기록한다.
- **응답 형식**: SimpleText만 보낸다. 말풍선은 기본 1개이고, 목표 길이를 넘으면 한 번 축약한 뒤 450자 기준으로 문장 경계에서 나눈다. 게이트웨이는 500자를 넘는 말풍선을 내보내지 않는다.
  - 동결 빌드 기준: 턴 p95 17.7초, 케이스당 말풍선 3.0개, 말풍선당 평균 218자
- **개발 방식**
  - 역할을 나눈 에이전트 세션 7개가 하나의 공유 보드로 협업했다(총괄·지식·연동·두뇌·테스트·분석·게이트).
  - 각 세션이 자기 경로만 쓰도록 훅으로 막았고, 훅이 없는 런타임은 사후 감사로 잡았다. 실제로 조정 도구에 대한 미공지 수정 2건을 감지해 원복했다.
  - 실행 결과를 성공/실패 장부에 남겨 실패한 방법은 반복하지 않았다. 장부에 빠진 실행 4건은 감사로 찾아 보완했다.
  - 계약(인터페이스)을 먼저 공표하고 병렬로 구현했다.

## 5. 아쉬운 점·한계

- **LLM 제공자 차단**: 레드팀과 합성 시험에서 인젝션·탈취 문구를 짧은 시간에 대량으로 보낸 뒤, 기존 Vertex 프로젝트가 이용 정책 사유로 모든 요청을 거부했다(남용 탐지로 추정). Gemini API 키 경로로 바꾸고, 명백한 탈취 문구는 모델에 보내지 않는 사전 필터를 넣고, 이후 인젝션 시험은 오프라인으로만 했다. 이 전환 과정에서 공개 TC가 일시적으로 12/15로 후퇴했다.
- **늦게 확보한 원문**: 회신 기한·영업일 달력·사업자 공시 같은 핵심 원문은 대회 후반에야 확보했다. 그 전 빌드는 잠정값으로 안내했고, 원문을 확보한 뒤 교체했다.
- **심사 유형 지식 공백**: 환불 입금 소요 기간 등 일부 항목(28개 중 8개)은 관계자 지식이 없어 일반 원칙 안내와 담당자 이관에 의존한다. "규정 밖 예외 요청"과 "단순 반발"의 경계는 KB 근거끼리도 엇갈려 판단이 흔들릴 수 있다.
- **지연과 길이**: KB와 규칙이 늘면서 턴 p95가 12.3초에서 17.7초로, 말풍선당 평균이 194자에서 218자로 늘었다. 정확도를 우선해 동결 전에 줄이지 않았다.
- **인터뷰 범위**: 관계자 10명 중 7명과만 대화했다. 초반 묶음 질문이 거절돼 시간이 들었고, 발굴률(./status)을 질문 배분에 충분히 쓰지 못했다.
